17. WAMDA TIMING MODEL
==================================================

This needs careful engineering.

We want the game to measure reaction speed, not simply:

"whose internet request reached Supabase first."

When the green trigger reaches a device:

Record a local high-resolution monotonic timestamp using an appropriate browser API such as:

performance.now()

When the participant taps:

record another local timestamp.

Reaction time:

tapTime - greenReceivedTime

Send the result to the server.

Persist:

participant_id
game_session_id
green_event_id
reaction_ms
submission_received_at
false_start
valid
integrity flags

The backend must validate:

- participant exists
- participant is eligible
- game is active
- correct game session
- exactly one attempt
- green signal was issued
- no duplicate submission
- reaction is within plausible bounds

Clearly flag suspicious impossible results.

For example, extremely low reaction times should not automatically win without integrity checks.

Do NOT rely exclusively on client-provided values without sanity validation.

For this student event, we do not need anti-cheat equivalent to professional esports, but we do want sensible integrity controls.

For equal/near-equal valid reaction results, use a clearly defined tie-break rule.

Document this rule.

==================================================
18. WAMDA — RANDOM DELAY
==================================================

The admin should NOT directly determine the exact green moment.

Workflow:

1. Admin presses:
ARM

2. Game enters armed state.

3. System chooses a random delay, e.g.:

2–7 seconds

4. After that delay, the server broadcasts the green event.

The admin should not know the exact delay.

This reduces anticipation based on the admin's physical movement.

Stage and participant phones must respond to the same game event.
