I. WAMDA — SERVER/BACKEND INTEGRITY
==================================================

Complete the real backend implementation.

Wamda remains a casual live-event reaction game, not professional esports, but implement sensible integrity checks.

Workflow:

Admin:
ARM

Server:
- verify admin
- create/identify active Wamda session
- create unique green event ID
- choose random secret delay between configured limits, e.g. 2–7 seconds
- transition to armed state

The exact green timing must not depend on a simple client-side Math.random().

At the chosen time:

server changes/broadcasts the authoritative GREEN state.

Participant devices receive the green event.

On each participant device:

use performance.now() to measure local reaction duration:

greenReceivedLocalTime
→ tapLocalTime
→ reaction_ms

Send attempt to secure backend.

Server validates:

- participant session is legitimate
- active Wamda session matches
- green event ID matches
- Wamda is active
- participant has not already attempted
- participant was not already false-started
- exactly one attempt per participant per session
- reaction_ms is positive
- reaction_ms is within a plausible range
- malformed/extreme values are rejected or flagged
- duplicates are rejected

If participant presses RED:

persist false_start = true

and prevent second attempt.

Winner selection:

valid attempts only.

Define and document deterministic tie behavior.

IMPORTANT FAIRNESS NOTE:

Client-measured reaction_ms cannot be made cryptographically cheat-proof because the browser is controlled by the participant.

Do not falsely claim perfect anti-cheat.

For this student event, implement practical sanity checks and flag suspicious values.

Admin must be able to see suspicious results before winner reveal if necessary.
